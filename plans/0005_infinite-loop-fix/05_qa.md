## 2. What doesn't

Ordered by how much it misleads the operator. None of these reintroduces a loop.

### Issue 1 — the table parser is not fence-aware, and the prompts hand the agent an unfenced `## Execution Status` example (medium)

`parseExecutionStatus` (`src/pipeline/execute-table.ts:280-286`) takes the **first** line matching
`/^#{1,6}\s+/` whose text contains "Execution Status", with no fence tracking. `operator-block.ts`
scans the same file fence-aware (`scanLines`, `isHeading`). Two modules, two rules for one file.

Both prompts deliver `EXECUTION_TABLE_SPEC`, whose worked example carries a literal
`## Execution Status` heading, **unfenced**:

```
$ npx tsx /tmp/qa-probe2.ts
planReviewPrompt: unfenced '## Execution Status' heading lines = 1
executeMilestonePrompt: unfenced '## Execution Status' heading lines = 1
```

A plan agent that quotes the contract into the playbook's Rules section — fenced or not —
before the real table hands the loop the example. Probe (`/tmp/qa-probe1.ts`), a fenced copy of
the spec's example above a real two-row table:

```
PROBE1 parsed rows: M1:agent:done, G1:operator:pending, M2:agent:pending | headerLine: 10
PROBE1 firstUnfinished: G1
```

Consequence: a zero-session pause at a gate that does not exist ("G1 — Operator merges PRs #12
and #14"), `setMilestoneStatus` rewriting the example's cell, and after the operator ticks, a
session on "M2 — Wire the parser into the loop" — a milestone from the example. Bounded, but the
wrong table is executed and the real one never moves. The M1 Notes cell flags this trap for
prompt *headings*; nothing defends the *file*. No fixture and no test covers a heading inside a
fence. The plan's tolerance list (§3 task 3) is silent on fences, so this is a robustness gap in
the class of bug the objective names ("a status table the regex cannot parse"), not a deviation.

### Issue 2 — `repoChanged` is decided by the commit the driver itself makes, so the plan-dir exclusion never applies (medium, wording only)

Plan M5 task 12 and §5.4: "with paths under `ctx.planPath` excluded — otherwise the agent
flipping its own status cell reads as 'made changes'". `repoSnapshot`'s `ignorePrefix` does
exclude those paths from `dirtyFiles`. But the driver takes the `after` snapshot **after**
`commitAll`, and `commitAll` runs `git add .`:

```
$ grep -n "repoSnapshot(git\|commitAll(git\|repoChanged(before" src/pipeline/handlers/execute.ts
480:    const before = await repoSnapshot(git, ctx.planPath);
492:    const hash = await commitAll(git, `vibe-racer: ${row.id} for #${ctx.taskNumber}`, ctx.cwd);
493:    const after = await repoSnapshot(git, ctx.planPath);
513:        repoChanged: repoChanged(before, after),
```

`repoChanged` (`execute.ts:304-308`) returns `true` on `before.head !== after.head`. Any edit
the agent makes to `04_execute.md` alone — a Notes cell saying why it cannot proceed, which the
playbook protocol step 7 tells it to write — is committed at line 492, moves `HEAD`, and the
pause block prints *"The agent committed work but did not finish this milestone. That is usually
an oversized milestone; review the commits, then resume or split the milestone"* for what is the
reported case exactly (an undeclared human-owned step). The other sentence is the right one.
`dirtyFiles` is effectively dead in this comparison because the snapshot after a successful
`commitAll` is always clean. The AC17 driver tests stub `repoSnapshot` with hand-picked heads
(`execute.test.ts:514-541`), so they cannot see the ordering. Stall *detection* is unaffected —
it is judged on the row, as the plan requires.

### Issue 3 — an unclosed fence anywhere earlier in the playbook hides the pause block, and resume fails silently (medium-low)

Probe: a `````bash` fence closed with ```` ``` ```` (CommonMark does not close it; neither does
`scanLines`, which requires `length >= fence.length`), then a real, fully ticked block:

```
PROBE2 findLastPauseBlock: null
PROBE2 readPauseBlockState: null
```

At pause time `normalisePauseBlock` no-ops and the terminal prints no checklist. At resume,
`resumeFromOperatorPause` returns `no_marker` (`advancement.ts:189-192`) and `driveCommand`
logs **nothing** on `advanced: false` (`drive.ts:105`) — the task is listed again under
"Waiting on operator" with the instruction to tick the marker they have already ticked. The
agent writes this file freely; a stray four-backtick fence, or a line like ```` ```js``` ````
at column 0, is enough. The failure has no diagnostic.

### Issue 4 — the agent's final message is dropped when it authored its own block (low)

`pause()` (`execute.ts:382`): `let next = reuse ? content : content + renderPauseBlock(input);`
— on the reuse path `input.agentMessage` (the `runAndStream` return value) is never written
anywhere. The driver test that covers this path returns `"I stopped at M1"` from the session and
does not assert it lands in the file (`execute.test.ts:651-693`), and it does not. The objective's
constraint reads "Nothing the agent explained is thrown away." The block does keep the agent's
`**Why paused:**` line, which is the substantive part.

### Issue 5 — `trailingOperatorRows` is status-blind at sign-off but status-filtered in the loop (low)

`signOffPlaybook` (`advancement.ts:125-126`) blocks the tick on any trailing operator row;
`announceTrailingRows` (`execute.ts:311-313`) filters `status !== "done"`. A plan whose author
pre-marked a trailing operator row `done` cannot be signed off, while the loop would walk past
it. The design says "status is the caller's filter" — one caller forgot.

### Issue 6 — `resumed_at` is never cleared after a gate resume (low)

`clearResumedAt` fires only in the run branch when the resumed row reaches `done`
(`execute.ts:519-521`). A gate row is settled to `done` by `settleRow` and never runs, so
`resumed_at: G1` stays in `state.yml` until the next pause clears it, or forever once the task is
at `ai_qa`. Cosmetic today; it would apply threshold 1 to any future agent row an operator
renumbers to that ID.

## 5. Risks and known limitations

For the decision checklist.

1. **Two markdown readers, two rules** (Issues 1 and 3). `execute-table.ts` ignores fences;
   `operator-block.ts` honours them. Until they agree, the same playbook can parse as one table
   for the loop and no pause block for resume. A fence-aware heading scan in the parser, and a
   `log.warn` from `drive` when a `need_operator` task returns `no_marker`, would close both.
2. **Stall wording is wrong whenever the agent touched only the playbook** (Issue 2). The block's
   diagnosis steers the operator toward "split the milestone" when the honest sentence is "this
   is a human step". Taking the `after` snapshot before `commitAll` — or comparing the commit's
   own file list against `ignorePrefix` — restores the design.
3. **A session-cap pause is treated as an overrule on resume.** `pause()` marks the row
   `needs_operator`, `settleRow` puts it back to `pending`, `resumed_at` is set, so the next
   `drive` gives that row **one** session before pausing as a stall (`thresholdFor`). A large,
   healthy milestone interrupted by the cap then costs one pause per `drive` until it lands in a
   single session. Bounded, documented nowhere.
4. **Secret scan on the agent's prose can strand a pause with a dirty tree.** The pause commit
   runs `commitAll` with the scan (`execute.ts:393`); the patterns include `sk-[A-Za-z0-9]{48}`
   and `ghp_…` (`secrets.ts:11-16`), which an agent quoting an example token would trip.
   `withErrorHandling` rethrows `SecretDetectedError` **before** `setError` (`safe-wrapper.ts:24`),
   so `state.yml` stays at `need_operator` (already written at `execute.ts:391`) with
   `04_execute.md` uncommitted — the opposite of the "clean working tree" the pause promises.
   Recovery is a hand edit to the block. No test covers it.
5. **`in_progress` at session end counts as a stall.** A session that runs out of context on a
   large milestone gets one retry, then pauses. Documented in `how-it-works.md`; worth knowing
   before writing five-file milestones.
6. **Legacy playbooks pay `MAX_STALLED_SESSIONS` per `drive`** on an undeclared human step until
   the operator adds an `Owner` column (D10, documented). This task's own playbook is one.
7. **The no-push rule is prompt-only** (follow-up #6) and **QA scope shrinks after a gate**
   (follow-up #7) — both declared in `docs/security.md` and `how-it-works.md`. `radio` runs
   outside the guard at every stage, including `need_operator`.
8. **`drive` still runs the advancement pass on whatever branch is checked out** (follow-up #8);
   the new branch hint only explains the silence.
9. **The AC1 "would hang" evidence is not reproducible from the repository** — by the plan's own
   design (scratch file, nothing committed). The Notes cell is the only record.
